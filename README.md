# ApiPostgresConnector

REST API коннектор для подключения к PostgreSQL базе данных.

## Описание

ApiPostgresConnector предоставляет REST API интерфейс для работы с базой данных PostgreSQL из любых приложений. Десктопное приложение с GUI интерфейсом на CustomTkinter и встроенным Flask API сервером.

Приложение поддерживает **несколько именованных подключений**: у каждого своя база данных и свои API-ключи. Клиент выбирает подключение именем в URL.

## Возможности

- 🌐 REST API для выполнения запросов к PostgreSQL
- 🖥️ GUI интерфейс настроек (CustomTkinter)
- 🔌 DSN подключение — ввод строки подключения в формате `postgres://user:pass@host:port/db`
- 🔐 API Key аутентификация — свои ключи у каждого подключения
- 🗂 **Несколько подключений** — список подключений с редактором параметров БД и ключами
- 🔑 **Генерация API ключа** — кнопка для создания нового ключа в GUI
- 📋 **Копирование API ключа** — кнопка для копирования ключа в буфер обмена
- 🔒 Шифрование паролей (Fernet)
- 📊 Просмотр таблиц и структуры базы данных
- 📱 Системный трей — сворачивание в трей с контекстным меню
- 📋 Вставка из буфера обмена — поддержка Ctrl+V с учётом позиции курсора
- 📖 Встроенная документация API
- 📝 **Опциональное логирование** — включение/выключение записи логов в файл
- 🔄 **Автоматическое переподключение к БД** при разрыве соединения
- 🩺 **Диагностика ошибок подключения** — причина ошибки в логе, в GUI и в ответе API
- ⏰ **Отображение последней активности** в системном трее

```bash
pip install -r requirements.txt

```

### Для клиента

**Достаточно передать один файл** — `ApiPostgresConnector.exe` (39,5 МБ). Это самодостаточная
onefile-сборка: Python, все библиотеки и ресурсы внутри. Ничего доустанавливать не нужно.

```
ApiPostgresConnector.exe      # ← всё, что нужно клиенту
```

При первом запуске рядом с EXE создаются:
```
ApiPostgresConnector/
├── ApiPostgresConnector.exe  # Приложение
├── config/
│   └── settings.json         # Настройки (создаётся при первом запуске)
└── app.log                   # Лог (создаётся при первом запуске)
```

> **Важно:** `config/settings.json` содержит пароли БД и API-ключи — не передавайте его клиенту,
> пусть приложение создаст файл самостоятельно. Если папка рядом с EXE недоступна для записи,
> настройки сохраняются в `%APPDATA%\ApiPostgresConnector\config\settings.json`.

> **Безопасность:** `config/settings.json` не коммитится в git. В репозитории лежит только
> обезличенный шаблон `config/settings.default.json`.

## Конфигурация

### Несколько подключений

Актуальная схема `config/settings.json`:

```json
{
  "connections": [
    {
      "name": "По умолчанию",
      "database": {
        "host": "localhost",
        "port": 5432,
        "database": "mydb",
        "user": "postgres",
        "password": "<зашифровано>"
      },
      "api_keys": ["your-api-key-here"]
    }
  ],
  "default_connection": "По умолчанию",
  "api": {
    "host": "127.0.0.1",
    "port": 5000,
    "debug": false
  },
  "gui": {
    "theme": "dark-blue",
    "width": 700,
    "height": 700
  },
  "app": {
    "auto_start_api": true,
    "minimize_to_tray": true,
    "enable_logging": true
  }
}
```

- `connections` — список подключений. У каждого свои параметры БД и **свои API-ключи**.
- `default_connection` — подключение, которое используется для запросов без имени в URL.
- Ключ подключения работает **только** со своим подключением.

**Миграция со старой схемы.** Если в конфиге нет `connections`, но есть блок `database` и `api.api_keys`,
приложение автоматически создаёт подключение «По умолчанию» и сохраняет конфиг в новом формате.

**В GUI (вкладка «Подключения»):**
- таблица подключений (имя, хост, порт, БД, пользователь, количество ключей);
- кнопки: «Добавить», «Переименовать», «Дублировать», «Удалить», «По умолчанию»;
- редактор параметров подключения: DSN, хост, порт, БД, пользователь, пароль;
- блок API-ключей **выбранного** подключения: отдельное поле основного ключа
  (📋 скопировать, 🎲 сгенерировать, 💾 сохранить) и список всех ключей подключения
  (+ добавить, 📋 скопировать, 🗑 удалить). Последний ключ удалить нельзя.

Изменения применяются к работающему серверу **сразу после «Сохранить настройки»** — перезапуск не нужен.

**Вкладка «Документация API»:**
- переключатель подключений — ссылки и готовые curl-команды пересобираются под выбранное подключение;
- у каждого эндпоинта кнопка «📋 Ссылка» (копирует только URL) и «cURL» (копирует команду с заголовком `X-API-Key`);
- «🌐» открывает в браузере только эндпоинты без авторизации (`/health`, `/info`).

### DSN подключение

Поддерживается подключение через DSN строку в формате:
```
postgres://user:password@localhost:5432/mydb
```

**В GUI:**
- Поле для ввода DSN строки
- Кнопка **"Из DSN"** — автоматически заполняет поля подключения (хост, порт, база данных, пользователь, пароль) из DSN строки

### API Key аутентификация

API ключи задаются **для каждого подключения**. Если у подключения нет ключей — аутентификация для него
не требуется. При создании подключения ключ генерируется автоматически.

При запросах передавайте заголовок:
```
X-API-Key: your-api-key-here
```

> **Важно:** браузер не умеет отправлять кастомные заголовки, поэтому по ссылке в адресной строке
> защищённые эндпоинты вернут `401`. Используйте curl, Postman или Python-клиент.

Проверить статус авторизации: `GET /api/v1/info` → поля `auth_required` и `api_key_count`.

Разные ответы при ошибке авторизации:

| Ситуация | Ответ |
|---|---|
| Заголовок не передан | `401 {"error": "Missing API key. Provide X-API-Key header"}` |
| Ключ не подходит подключению | `401 {"error": "Invalid API key for connection \"<имя>\""}` |

### Режим отладки

В конфигурации `config/settings.json` доступна опция `debug`:
```json
{
  "api": {
    "debug": true
  }
}
```

При `debug: true`:
- Flask отображает детальные сообщения об ошибках с трассировкой стека
- Полезно для разработки и диагностики

> **Внимание:** Не рекомендуется использовать режим отладки в продакшене.

### Опциональное логирование

В конфигурации `config/settings.json` доступна опция `enable_logging`:
```json
{
  "app": {
    "enable_logging": true
  }
}
```

При `enable_logging: true` логи записываются в файл `app.log` (рядом с EXE или в корне проекта).
При `enable_logging: false` логи пишутся только в консоль.

> Управлять логированием также можно через GUI на вкладке "API" — переключатель "Ведение логов в файл".

### Шифрование паролей

Пароли автоматически шифруются при сохранении конфигурации. Для дополнительной безопасности можно
установить переменную окружения:
```bash
set ENCRYPTION_KEY=your-base64-encoded-key
```

> **Важно:** без `ENCRYPTION_KEY` ключ шифрования выводится из имени машины (`platform.node()`),
> поэтому конфиг с паролем нельзя переносить на другой компьютер. Для переноса задайте одинаковый
> `ENCRYPTION_KEY` на обеих машинах.

### Системный трей

Приложение поддерживает работу в системном трее:

- При нажатии кнопки **Свернуть** приложение сворачивается в трей
- Иконка в трее отображает статус API (запущен/остановлен) и последнюю активность
- Контекстное меню в трее:
  - **Показать окно** — восстановить окно приложения
  - **Запустить API** / **Остановить API** — управление сервером
  - **Выход** — закрыть приложение

### Автоматическое переподключение к БД

Приложение автоматически отслеживает состояние подключения к базе данных и выполняет переподключение при разрыве соединения:

- При запуске приложение подключается к БД в **фоновом потоке** — запуск GUI и ответы API не блокируются
- При потере соединения приложение пытается переподключиться автоматически
- При обрыве во время запроса запрос повторяется один раз на новом соединении
- После неудачной попытки следующая попытка делается не раньше чем через 30 секунд (чтобы запросы не висели)
- Информация о статусе подключения отображается в GUI: строка «БД: подключено» / «БД недоступна: <причина>»
- В случае успешного переподключения API продолжает работу без перезапуска

Проверить состояние можно запросом (не требует ключа):
```
GET /api/v1/health → {"status": "ok", "database_connected": true, ...}
```
Если `database_connected: false`, в ответе будет поле `last_error` с типом ошибки и причиной.

> Состояние в `/health` отражает **подключение по умолчанию**. Для другого подключения:
> `GET /api/v1/c/<имя_подключения>/health` (с заголовком `X-API-Key`).

### Вставка из буфера обмена

Поддерживается вставка данных через **Ctrl+V**:

- Вставка работает с учётом текущей позиции курсора
- Поддерживается замена выделенного текста
- Работает во всех текстовых полях GUI (параметры подключения, API-ключ, вкладка «API»)
- Текст вставляется ровно один раз: обработчик привязан к самому полю ввода, а не к окну целиком
- По правой кнопке мыши доступно контекстное меню «Вставить»

## API Endpoints

Запросы без имени подключения работают с подключением по умолчанию.
Именованный вариант — `/api/v1/c/<имя_подключения>/...`.

| Метод | Эндпоинт | Описание |
|-------|----------|----------|
| GET | `/api/v1/health` | Состояние API и подключения к БД |
| GET | `/api/v1/info` | Информация об API |
| GET | `/api/v1/tables` | Список всех таблиц |
| GET | `/api/v1/tables/<name>/columns` | Колонки таблицы |
| GET | `/api/v1/tables/<name>/select` | Выборка из таблицы |
| POST | `/api/v1/tables/<name>/insert` | Вставка одной записи |
| POST | `/api/v1/tables/<name>/batch-insert` | Массовая вставка (массив) |
| POST | `/api/v1/query` | Выполнение SQL запроса (только SELECT) |
| GET | `/api/v1/c/<имя>/tables` | То же для именованного подключения |

Все эндпоинты, кроме `/health` и `/info`, требуют заголовок `X-API-Key` **для выбранного подключения**.

## Примеры использования

### Python
```python
import requests

BASE = "http://127.0.0.1:5000/api/v1"
HEADERS = {"X-API-Key": "your-api-key"}

# Проверка здоровья API (без ключа)
response = requests.get(f"{BASE}/health")
print(response.json())

# Таблицы подключения по умолчанию
tables = requests.get(f"{BASE}/tables", headers=HEADERS).json()

# Таблицы именованного подключения
tables = requests.get(f"{BASE}/c/crm/tables", headers=HEADERS).json()
```

### cURL
```bash
# Проверка здоровья
curl http://127.0.0.1:5000/api/v1/health

# Таблицы с API-ключом
curl -H "X-API-Key: your-api-key" http://127.0.0.1:5000/api/v1/tables

# Именованное подключение
curl -H "X-API-Key: your-api-key" http://127.0.0.1:5000/api/v1/c/crm/tables
```

### PowerShell
```powershell
Invoke-RestMethod -Uri "http://127.0.0.1:5000/api/v1/tables" `
    -Headers @{ "X-API-Key" = "your-api-key" }
```

### Массовая вставка

```bash
curl -X POST -H "X-API-Key: your-api-key" -H "Content-Type: application/json" \
     -d '[{"name":"Ivan","phone":"+79991234567"},{"name":"Petr","phone":"+79997654321"}]' \
     http://127.0.0.1:5000/api/v1/tables/users/batch-insert
```

Особенности `batch-insert`:
- максимум 1000 записей за один запрос;
- все объекты должны содержать одинаковый набор колонок (иначе `400` — данные не теряются молча);
- если таблицы нет — она создаётся автоматически (все колонки `TEXT` + `parsed_at TIMESTAMP`);
- числовые строки приводятся к `int`/`float`, `"true"`/`"false"` — к `bool`.

## Решение проблем

| Симптом | Причина | Что делать |
|---|---|---|
| `401 Missing API key` | Запрос сделан без заголовка `X-API-Key` | Добавьте заголовок (браузером нельзя) |
| `401 Invalid API key for connection "..."` | Ключ от другого подключения или опечатка | Возьмите ключ у нужного подключения во вкладке «Подключения» |
| `404 Unknown connection: ...` | Имя подключения в URL не найдено | Проверьте имя в таблице подключений |
| `503 Database connection lost` + `reason` | Нет связи с БД | Смотрите `reason.kind` и подсказку, либо `app.log` |
| `database_connected: false` в `/health` | БД недоступна или ещё подключается | Причина — в `last_error`; в GUI — строка «БД недоступна» |
| `Cannot start API — порт занят` | Порт уже слушает другой процесс | Закройте другой экземпляр или смените порт на вкладке «API» |
| Настройки не применяются | Не нажата кнопка «Сохранить настройки» | Нажмите её — изменения применяются без перезапуска |

### Диагностика ошибок подключения к БД

Причину ошибки подключения можно получить в трёх местах:

1. **В лог** (`app.log`) — одна строка с типом ошибки и подсказкой:
   ```
   Database connection failed [auth_failed]: password authentication failed for user "nocodb" — Неверный пользователь или пароль
   ```
   Подробности (`detail`, `hint`, SQLSTATE) — на уровне DEBUG.
2. **В GUI** — вкладка «Подключения», строка состояния под выбранным подключением; то же в тултипе трея.
3. **В API** — `GET /api/v1/health` → `last_error.kind` и `last_error.message`; в ответах 503/500 →
   `reason` с `kind`, `detail`, `hint`, `sqlstate` и `user_hint`.

Типы ошибок (`kind`):

| kind | Симптом | Что делать |
|---|---|---|
| `auth_failed` | password authentication failed | Проверьте пользователя и пароль |
| `permission_denied` | permission denied | Проверьте привилегии пользователя БД |
| `refused` | connection refused | Проверьте, что PostgreSQL запущен и порт указан верно |
| `dns` | could not translate host name | Проверьте DNS и сетевой доступ |
| `timeout` | timeout expired | Проверьте доступность хоста и файрвол |
| `does_not_exist` | database does not exist | Проверьте имя базы данных |
| `too_many_connections` | too many clients | Увеличьте лимит соединений на стороне БД |
| `shutdown` | terminating connection | Соединение закрыто администратором БД |
| `ssl` | SSL-ошибки | Проверьте `sslmode` и сертификаты |
| `encoding` | UnicodeDecodeError | Проверьте `PGCLIENTENCODING=UTF8` |
| `query_error` | прочие ошибки SQL | Смотрите `detail` и `hint` в `app.log` |

Таймаут подключения — 10 секунд (`connect_timeout`), поэтому недоступный хост не «вешает» приложение.
После неудачной попытки следующая попытка делается не раньше чем через 30 секунд — повторные запросы
к недоступной БД отвечают сразу, используя запомненную причину ошибки.

## Сборка EXE

```bash
pip install -r requirements-dev.txt
pyinstaller pyinstaller.spec
```

Результат — один файл `dist/ApiPostgresConnector.exe` (onefile: библиотеки внутри).

Номер релиза задаётся в одном месте — `src/version.py` (`APP_VERSION = "2.1.0"`). Он попадает:
- в свойства файла EXE (Windows → «Сведения» / «Свойства»);
- в заголовок окна приложения;
- в ответ `GET /api/v1/info` → `"version"`;
- в подвал встроенной документации;
- в ресурс версии, который spec генерирует из `src/version.py` (дублировать руками не нужно).

При смене версии достаточно поправить `src/version.py` и пересобрать.
